작성일: 2026-11-16 · 대상: `main` (`42b25f1`, PR #6 머지 시점)

## 요약

PR #3(CDH 구현)을 기준으로 #2·#4의 일부를 가져와 통합한 6단계 커밋을 모두 다시 빌드해 같은 테스트를 돌렸습니다. **최종 단계(`215029f`, 현재 `main`과 같은 코드)는 모든 검사를 통과했고, 어느 단계에서도 앞 단계보다 나빠진 결과(회귀)는 없었습니다.**

- 단위·기능 테스트 93개는 6단계 모두 기본, ASan, release 빌드에서 전부 통과했습니다. 단, 첫 단계의 release 빌드는 실행 자체가 되지 않았습니다.
- 통합 중에 원래 #3에 있던 문제 2개를 찾아 고쳤습니다.
  1. **`make release` 무한 재귀:** make 프로세스가 61개까지 늘어나 멈췄습니다. `43b71bf`에서 고쳤습니다.
  2. **프로토콜 오류 문구:** 실제 Redis와 문구가 달라 호환성 테스트 2개가 실패했습니다. `73bb212`에서 고쳤습니다.
- 같은 호환성 테스트를 실제 Redis 7.0.15에 돌려도 통과합니다(121 통과, 1 건너뜀). 테스트의 기대값 자체가 맞다는 뜻입니다.

## 테스트 방법

각 커밋을 별도 작업 폴더(git worktree)로 꺼내 빌드 산출물 없이 처음부터 빌드하고, 아래 검사를 차례로 실행했습니다.

- **환경:** Linux 컨테이너, gcc, GNU make, Python 3, redis-cli 7.0.15. 비교 기준으로 실제 Redis 7.0.15를 띄웠습니다.
- **그 단계에 들어 있는 테스트:**
  - `make -C CDH test`: 단위 6개 스위트(76개)와 기능 1개 스위트(17개)
  - `make -C CDH asan`: 같은 테스트를 ASan/UBSan 빌드로 실행
  - `make -C CDH release`: 같은 테스트를 `-O2 -DNDEBUG` 빌드로 실행
  - `make -C CDH smoke`: 실제 서버 바이너리를 띄워 확인
- **공통 회귀 테스트:** 최종 커밋의 테스트 파일을 모든 단계의 서버 바이너리에 똑같이 돌렸습니다. 테스트가 아직 없던 단계도 같은 기준으로 비교하기 위해서입니다.
  - 최종 `smoke.sh` (강제 종료 복구 포함 8항목)
  - `redis_compat.sh` (redis-cli 호환성 124개)
  - `test_cache_api.py` (HTTP 캐시 예제)
- **설정 검사:** `docker compose config -q`로 각 단계의 `compose.yaml` 문법을 확인했습니다.
- **release 빌드 안전장치:** 1단계는 make가 자기 자신을 끝없이 부릅니다. 그래서 make 프로세스가 50개를 넘으면 프로세스 그룹째 종료하고 "폭주"로 기록했습니다.

## 단계별 상세

### 1단계 `32e0d1d` — #3 원본

- `test`, `asan`, `smoke`는 모두 통과했습니다.
- **`make release`가 끝나지 않습니다.**
  - 원인: `VARIANT=release`이면 `bench/bench.mk`의 벤치마크용 라이브러리 경로가 `Makefile`의 `$(LIB)`와 같은 파일이 됩니다.
  - 그 파일을 만드는 규칙이 "release로 다시 make 호출"이어서 make가 자기 자신을 끝없이 부릅니다.
  - 측정 시 make 프로세스가 61개까지 늘어나 강제로 종료했고, 실제 작업 중에는 메모리 부족으로 다른 프로세스까지 죽었습니다.
- **호환성 테스트 2개 실패:** 둘 다 `$` 자리에 다른 바이트가 온 경우입니다.

  | 테스트 | 기대값 (실제 Redis) | 실제 결과 |
  |---|---|---|
  | `first-request protocol error: reply` | `-ERR Protocol error: expected '$', got 'X'` | `-ERR Protocol error: expected '$'` |
  | `missing $: reply` | `+PONG`, `-ERR Protocol error: expected '$', got 'X'` | `+PONG`, `-ERR Protocol error: expected '$'` |

- 강제 종료 복구는 이 단계부터 이미 통과합니다. 기능은 처음부터 있었고, 테스트만 5단계에서 추가했습니다.

### 2단계 `43b71bf` — release 무한 재귀 수정

- `bench.mk`에서 `VARIANT=release`일 때는 재귀 규칙을 정의하지 않게 했습니다.
- **`make release`가 통과했습니다(93/93, make 프로세스 최대 3개).** 다른 결과는 1단계와 같아 회귀가 없습니다.

### 3단계 `73bb212` — 프로토콜 오류 문구 수정

- 받은 바이트를 넣어 `expected '$', got 'X'`로 응답하게 했습니다. 이 문자열을 담으려고 파서 구조체에 48바이트 버퍼를 추가했습니다.
- **호환성 테스트가 124/124로 올라갔습니다.** 나머지 검사는 그대로 통과합니다.
- 오류 문자열이 이제 파서 안에 저장되므로, 파서를 해제한 뒤 문자열을 읽던 단위 테스트 헬퍼를 같은 커밋에서 고쳤습니다.
  - 이 문제는 커밋 전 ASan 실행에서 `stack-use-after-return`으로 발견했습니다.
  - 서버 코드는 파서가 살아 있는 동안에만 문자열을 쓰므로 영향이 없습니다.

### 4단계 `daaf35a` — Docker 환경

- C 코드 변경이 없어 테스트 결과는 3단계와 같고, `compose.yaml` 문법 검사도 통과했습니다.
- 이 환경에서는 이미지를 빌드할 수 없었습니다(Debian 패키지 서버 차단). 대신 Windows Docker Desktop에서 다음을 확인했습니다.
  - 이미지 빌드가 성공했고 헬스체크가 Healthy였습니다.
  - `PONG`, `SET`/`GET`, 재시작 후 AOF 복구(`"world"`)가 모두 정상이었습니다.
  - 그 PC에서는 다른 프로그램이 6379를 쓰고 있어 `MINI_REDIS_PORT=6390`으로 실행했습니다.

### 5단계 `15a84ab` — 테스트·예제 추가

- 그 단계의 `smoke`가 6항목에서 8항목이 됐습니다(강제 종료 복구와 그 후 정상 종료).
- `make compat`과 `make example-test`가 이 단계에서 생겼고 둘 다 통과합니다. 기존 93개 테스트는 그대로 통과합니다.

### 6단계 `215029f` — 문서

- README만 바뀌었고 결과는 5단계와 같습니다. 이 커밋의 코드가 현재 `main`(`42b25f1`)과 같습니다.

## 확인하지 못한 항목

- Docker 이미지 빌드는 이 테스트 환경에서 실행하지 못했습니다. Windows Docker Desktop에서 수동으로 한 번 확인한 결과가 전부입니다.
- 실제 Redis 8과의 비교는 하지 못했습니다. 이 환경에는 Redis 7.0.15만 있었습니다.
- Windows 개발 컨테이너 안에서 `make -C CDH test`는 실행하지 않았습니다.
- 각 테스트는 한 번씩만 실행했습니다. 타이밍에 따라 가끔 실패하는 테스트가 있는지는 확인하지 않았습니다.
